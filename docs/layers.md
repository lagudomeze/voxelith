# 三层架构职责（R8–R19、R112–R115）

## 0. 一句话

**数据归数据，公式归公式，执行归执行，表现归表现。**（R112）
**L0 是砖块，L1 是搭砖规则，L2 是画出来的建筑。**（R113）
**通过事件通信，绝不越界。**（R114）

## 1. 分层总表

| 层 | 名字 | 位置 | 一句话职责 | 允许依赖 |
|---|---|---|---|---|
| L0 | `atoms` | `voxelith-axiom` | 原子数据 + 只碰自己的系统 | 只有自己所在模块 |
| L1 | `behaviors` | `voxelith-axiom` | 需要多个组件同时存在才生效的逻辑 | L0 |
| L2 | prime | `voxelith-prime` | 表现、内容、驱动（输入/AI） | L0、L1、完整 Bevy |

> R19：L1 用 `behaviors` 命名，**不用** `relations`。因为 L1 不限于两两关系（例：装备栏是三组件组合）。

## 2. L0：atoms

允许：

- 组件只依赖自己。（R8）
- 系统只查询自己，不跨组件查询。（R8）
- 可以发出事件，事件只含**数据**，不含渲染句柄。（R9）

禁止：

- `Sprite`、`Text`、`Mesh`、`Transform`、`Handle<Image>`。（R10、R103）

判断一个东西是不是 L0：**把这个组件单独拿出来，它的系统能不能只靠它自己跑通？** 能 → L0。

L0 的典型成员：`Health`、`Lifetime`（R61、R63）、纯数值事件定义与执行系统。

## 3. L1：behaviors

定义：需要多个组件同时存在才生效的逻辑。（R11）

允许：

- 可以依赖 L0。（R12）
- 跨模块监听事件（`MessageReader` 不关心事件谁注册）。（R38）
- 可以在不知道具体层的情况下做判定、公式、筛选。（R54、R59）

禁止：

- 不得依赖 L2。（R12）
- 修改 L0 数据**必须通过事件**，不直接改。（R13）
- 禁止生成渲染实体（`SpriteBundle` 等），禁止依赖渲染 crate。（R14、R99）

### 为什么 L1 不能直接改 L0

如果 L1 能直接写 `Health`，那么"谁改了血量"就不可追踪，L0 的"唯一写入口"保证失效（R56）。事件是**唯一通道**，好处是：

1. 所有数值变化都留下一条可观察的记录。
2. 表现层可以旁路监听（R55）。
3. 公式可以层层拦截修改（R54）。

## 4. L2：prime

允许：

- 只读 L0/L1 数据，通过事件监听变化。（R15）
- 使用完整 Bevy、渲染组件、UI。（R18）
- 拥有驱动源：输入、AI 决策、场景编排。

禁止：

- 禁止直接修改 `Health`、`Velocity` 等核心数据。（R16）
- 禁止写战斗公式、伤害计算。（R17）
- 禁止越界反向定义核心规则（"因为表现需要，所以在 L2 里算一下伤害"是典型违规）。

## 5. 越界速查

| 想做的事 | 错误做法 | 正确做法 |
|---|---|---|
| L2 想让怪物掉血 | 直接 `*health = ...` | 发 `DamageRequest`，等 L1 → L0 处理 |
| L1 想改血量 | 直接改 `Health` | 发 `ModifyHealthMessage`，由 L0 `health` 执行 |
| L1 想显示命中特效 | 在 L1 生成 `SpriteBundle` | L1 发事件；L2 监听并生成表现 |
| L0 想读位置做判定 | 查询 `Transform` / 其它组件 | 位置由 L0 自己的组件承载；判定放 L1 |
| L2 想算减伤 | 在 L2 写公式 | 公式属于 L1，L2 只读结果与事件 |

## 6. 命名与组织总则

- 按**功能**组织，不按类型组织。（R115）
- 模块按功能领域命名，不按技术角色命名。（R20）
- 详见 [file-layout.md](file-layout.md)、[naming.md](naming.md)。

## 7. 分层自检清单

写代码前问自己 5 个问题：

1. 我这一层的**唯一职责**是什么？（数据 / 公式 / 执行 / 表现）
2. 我要改的数据属于哪一层？我有没有资格写它？
3. 如果我需要跨层，是不是应该发事件？
4. 我引用的类型，是不是把上层的东西拖下来了？
5. 我的模块名是领域名还是角色名（`base`/`utils`）？

## 8. L0 / L1 测试约定

- **用 `App::new()` + 被测模块自己的 Plugin**，不要用 `MinimalPlugins`：
  `MinimalPlugins` 属于 `bevy_internal`（`bevy` facade），`axiom` 只有 `bevy_app`，**导不进来**。
  `App::new()` 自带 `MainSchedulePlugin`，`app.update()` 就能跑。
- 测试放 `crates/voxelith-axiom/tests/`（集成测试）或模块内 `#[cfg(test)]`（需要访问私有字段时）。
- 需要断言"没有消息就不重算"这类**私有状态**（如缓存版本号）时，用模块内单测；
  行为契约（数值结果）一律写集成测试，顺便固化 Message/Event 用法。

## 9. 配置与数据约定（I6）

- **所有可调参数都放 Resource**（`XxxConfig`），不写死在系统里：`StatConfig`、`ModifierCaps`、
  `ResistanceCaps`、`PipelineConfig`、`RollConfig`、`StatusConfig`、`ContestParams`、`LevelConfig`。
- 各 L1 域的配置由内容层聚成一份 `CombatConfig` 注入，`CombatPlugin` 分发到子域；
  子域自己的 `init_resource` 只在"独立使用 / 单测"时兜底（`insert_resource` 先执行时不会被覆盖）。
- **L0/L1 不读文件、不碰 `AssetServer`**（R101 精神）：文件加载与反序列化都在 L2，
  读完把值塞进 Resource。这样 L0/L1 仍然能在无渲染、无文件系统的环境里跑测试。
- 事件定义在**发出它的模块**（R33）；但**改 L0 数据的入口消息定义在 L0**（如 `ModifyHealthMessage`、
  `GrantStatPointsMessage`），由 L1/L2 发出——契约属于数据的拥有者。
- **组件自成一体**：如果最终值只依赖组件自己的字段（`Stat`、`Resistance`），就让组件在收到变更消息后
  **自己刷新缓存**，不要造"脏了 / 算好了"的来回消息。只有"必须别的组件同时在场才能算"的部分才放 L1。
  判断标准很简单：**公式需要的信息如果都在这个组件里，它就不需要跨层**（R8 自然成立）。
