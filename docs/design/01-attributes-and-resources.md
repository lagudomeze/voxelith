# 属性与资源

这一篇定**可修正的量（属性与资源）**的模型，与引擎无关。数值公式的具体取值属数值阶段；Bevy 侧的写法见 [bevy/](bevy/README.md)。

组件形状的跨主题前提见 [组件约定](00-component-conventions.md)。

**上游需求**：`SY-01`…`SY-08`、`SY-30`…`SY-34`、`SY-53`、`SY-56`、`SY-58`、`SY-59`、`GP-24`、`GP-39`、`GP-44`

## 一、可修正的量：两种形状，不需要泛型载体

**修正指向的是一个类型**——“力量”这个类型、“血量上限”那个类型。量只有两种形状：

| 形状 | 怎么定义 | 例子 |
| --- | --- | --- |
| **单值型** | 一个 newtype，**它自己就是自己的标记** | 力量、敏捷、护甲、移动速度、挖掘力 |
| **资源池型** | 当前值 + 基础上限；**上限有自己的标记**（一个资源有两个值） | 血量、精力、法力、悖论 |

- **单值型**：读出来的就是“基础值 + 修正”。
- **资源池型**：**只有当前值是状态**（由事件改，不走修正）；**上限与单值型共用同一套修正**——所以“这件装备 +20 血量上限”与“+5 力量”是同一种东西。
- **不要泛型载体**：`Value<M>` 那种写法是多余的。单值型把标记指成自己就够了，还省掉一层命名；资源池只需要一个“上限”的标记。
- **资源只有一个量可修正：上限。** 没有“修正当前值”这回事——当前值的变化全是**事件**（伤害、治疗、回复）写进去的；如果它也挂修正层，“每次挨打先写基础值、每次读再叠一层”会把最热的那条路复杂化，还会和“上限降低时夹取当前值”的规则两头打架。
- 好处：十几项属性、若干条资源，共用两种形状和**一条读取路径**；加一项属性就是照抄七行（一个 newtype + 一句读出实现），不上宏——少一层间接，读和改都更直接。

## 二、修正

一个修正 = **一个实体**，带一份修正。

**“修正怎么挂到被修正的角色身上”不属于这一层**——装备、增益、只在某个条件下生效的东西，生命周期与生效规则各不相同，**哪些修正算数由用到它的系统决定**（`SY-33` 的“移除即失效”因此落在各自的挂法上）。读出规则只吃“基础值 + 一串修正”，谁调用谁决定喂什么。

| 修正 | 含义 |
| --- | --- |
| **平加** | 绝对值（`+5 力量`） |
| **比例** | **按基础值**的比例（`+50% 基础力量`）——不是按"已经加过别的修正之后的值" |

**一条修正可以同时带两者**（`+5 力量` 且 `+50% 基础力量`）——它们分开算、再相加，所以叠加依然可交换。

**两条来源**：

- **外部来源**（装备、增益、减益）：各自有生命周期，挂在主人旁边的实体上；
- **派生来源**（主导属性对派生量的影响，如"体质 → 血量上限"）：**写在主人自己身上**的一条修正，由 system 维护。

也就是说：**“修正”就是一条**，只是它可以住在两个地方——**自己身上那条**（派生写这里；一个量只能有一条）与**挂着的那些实体**（装备/增益，可以有很多条）。重算时两处一起求和。

## 三、读出：一条规则，两个半边

规则只有一条：

```
有效值 = 基础值 + Σ每条修正的贡献(基础值)
```

“贡献”由**修正自己**回答：**平加**的贡献是它的数值（与基础值无关）；**比例**的贡献是 `基础值 × 它的比例`。这条式子可交换、可并行，也不会指数增长。

它被拆成**两个半边**，因为“哪些修正算数”是具体项目的事（装备、增益、条件效果的生命周期各不相同）：

| 半边 | 谁做 | 知道什么 |
| --- | --- | --- |
| **求和并写缓存** | 项目的重算系统（`voxelith_rules::recompute`） | 知道**修正怎么挂**（装备槽？增益列表？自己身上那条？） |
| **读** | 任何系统 / UI | **只读缓存**（`Total<量>`），一个挂法都不认识 |

**有效值缓存在 `Total<量>` 里**，每个量一出生就自动带一份（`#[require]`），所以 `bsn!` 里不用写它。这么做换来两个结果：

- **`SY-58`（面板上的数就是进公式的数）从约定变成结构**：只有一个数，读的人不可能拿到"另一份和"；
- **读出口统一**：伤害、UI、AI 都只读 `Total`，不再各自拿一串修正去求和。

**代价与纪律**：缓存必须**在读者之前**重算；`Total` 初值等于基础值（不会读到 0），但顺序错了会读到**上一帧**的数——所以重算按阶段排序（见[派生](#六派生量由属性算出来)那节的三段）。

**资源的有效值就是上限**（`Total<Max<资源>>`）；当前值不走这条规则，它是状态。

**这条式子的三条性质**（都是选它的理由）：

| 性质 | 为什么成立 |
| --- | --- |
| **顺序无关** | 全是加法归约，修正的登记顺序不影响结果 |
| **可并行** | 每个修正只依赖"基础值 + 它自己"，彼此不依赖 |
| **不会指数增长** | 不做"比例乘比例"（`Π(1+r)`：堆十个 +50% 就是 1.5¹⁰ ≈ 58 倍） |

**明确不做**：覆盖（"直接设为 20"）与任何依赖顺序的修正。修正层只管加成；**下限、曲线这类"读出来之后再处理"的规则，属于用它的 system**。

**连带改了需求**：本设计让 `SY-08` 的"减速收益递减"失效（加法叠加下减速是线性的，相对效应反而递增），已把该条改成只要求"**速度恒为正**"（2026-10-09）。

**一条护栏（与 `SY-16` 同理，只是反着来）**：**"减少型"的比例必须有下限**。减速、减消耗、减冷却这类，纯加法叠加能一路堆到 0 甚至负数，而"0 冷却 / 0 消耗"会让机制直接失效。所以这类量的比例和要有下界（具体值属数值阶段）。

## 四、资源的具体规则

- **三条资源**：血量与精力人人都有，**法力按角色配置**（`SY-01`）；之后还会有专属资源（悖论、均衡、仇恨，`SY-30`）。每条资源三个量：当前值（状态）、基础上限、基础**回复速率**（每秒多少，时间单位是秒）。
- **上限与回复速率都可修正**，当前值**不走**修正——它是状态。
- **改动只能通过事件**：伤害、治疗、回复都发同一条消息（`Adjust`），它是当前值的**唯一写入口**——"治疗与扣血走同一条通路"（`SY-17`）因此不是口号而是结构。消息上带着**谁改的**，给日志留着（`SY-05`；真正的记录还没做）。
- **core 不夹取、不判死**：夹到上限需要**算出来的上限**，而"修正怎么挂"是应用侧定的，core 拿不到 ✗ → **上限夹取、上限降低时的压缩都留在拿到上限的那一层**。资源可以为负，负值意味着什么由**各自的 system** 决定：血量 ≤ 0 由死亡 system 判定（`GP-24`），精力为负由释放与冲刺的 system 自己检查。
- **上限降低时**（卸下加血量的装备、中了减上限的效果）：当前值夹到新上限，**夹取绝不致死**（至少保留 1 点）——由拿到上限的那一层做。
- **变动规则是一组独立组件**：每秒回复、不回复、动态衰减、挨打才涨、越高越糟、绝对上限……资源不是"一种东西"，而是"**一个数值 + 一串规则**"（`SY-06`）。将来加"悖论法师""自然守护者"这类角色，是**换一组规则**，不是加代码。（规则组件本体还没做。）

## 六、派生：量由属性算出来

“体质 → 血量上限”这类关系叫**派生**。它卡在“基础值 / 修正 / 读出”三者之间，只有三种接法：

| | 谁干活 | 读出脏不脏 | 代价 |
| --- | --- | --- | --- |
| **A. 变更时写进修正**（选用） | 一个 system：属性变了就更新那条修正 | **不脏**——读的人看到的还是普通修正 | 一帧延迟；每个量一条自派生规则 |
| B. 读出时算 | 读的人（得顺手拿到属性） | **脏**：读出不再只吃“基础值 + 修正”，还得认识属性；core 也要认识“血量上限依赖体质”这条**具体规则** | 与 `SY-59`（公式在代码、参数在内容）冲突 |
| C. 出生时烤进基础值 | 创建/升级时 | 最快 | 仍要一个“属性变了重算”的 system（白搭）；`base_max` 变成推导出来的状态，和“上限降低夹取当前值”纠缠；也分不清“体质给的上限”和“装备给的上限” |

**选 A**，理由是**同构**：派生写出来的修正与装备给的修正长得一模一样，所以读出口只有一个（`基础值 + Σ修正`），日志/预览天然统一。

具体形状：

- **一条派生 = 主人自己身上的一组组件**：一条“`To` 由 `From` 算出来 + 用哪份配置”的声明，和**结果那条修正**（写在自己身上，与装备给的修正完全同构，所以一个量只能有一条自派生规则）。
- **派生读的是有效值**（`Total<From>`），不是基础值——所以“装备 +5 体质”会真的抬高血量上限（`SY-58`）。
- **公式在代码，参数在内容**（`SY-59`）：一份配置文件 = 一条规则的参数（“每点体质 +5”），可改、可复用、可热重载。**“有哪些规则、挂在谁身上”留在 `bsn!` / 模板里**——结构在模板、参数在文件，资产坏了最坏是数值不对，不会让结构缺失。
- **只把“可变动的参数”放进文件**：公式本身（乘法？曲线？）在代码里。
- **派生用平加**（`flat`）：”每点体质 +5“是绝对量，不是“基础上限的百分比”；用比例语义就错了（比例留给“按基础值的百分比”）。
- **出错策略**：缺配置（模板里漏了）→ **报错**；还没加载好 → **报错**。**"等资产"是装配层的事**（进游戏前等齐，真实项目里就是加载界面）——system 里不要有"还没到货"这条分支，也**绝不用默认值糊过去**。
- **只在值真的变了才写**：否则每帧写会连锁触发下游的变更检测；顺带好处是配置热重载自动生效。
- 接受**一帧延迟**：等级一加，下一帧上限才变。所以一帧里必须分三段跑：

```
属性重算（Total<属性>）→ 派生写修正 → 回复速率与资源上限重算（Total<上限>）
```

- 只有出现“**派生量再被派生**”（等级→力量→血量上限）时才需要再加一段；目前的输入都是属性（`SY-56` 每个资源各自声明主导属性），三段够了。

派生修正**与外部来源（装备/增益）在读出上完全同构**，而且读的人只看 `Total`，所以这套不需要读出方配合——这是它相对 B、C 最大的好处。
