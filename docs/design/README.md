# 编码设计

**边界**：这里回答"怎么做"——模块划分、数据流、数据结构、并发与性能取舍。**不写**"要什么"（那属于 [requirements/](../requirements/README.md)）。设计过程中发现需求缺口，回需求目录登记 `Q-xxx`，不要在这里替用户拍板。

## 两条线

| 目录 | 路线特征 | 状态 |
| --- | --- | --- |
| [bevy/](bevy/README.md) | 全 Rust，自己掌控渲染与调度；用 Bevy 的 ECS 与插件体系 | 待评估 |
| [godot/](godot/README.md) | 引擎负责渲染/编辑器/场景；Rust 走 GDExtension，或 GDScript 为主 | 待评估 |

选型结论写到 `engine-decision.md`（**待写**，对应 [Q-001](../requirements/open-questions.md)）。结论落定前两条线各自成立，**不要把一条线的假设写进另一条**；需要两边都认的事实，写进对应需求条目而不是设计文档。

## 共同约束

- 每条设计都要引用它服务的需求条目（`REQ-xxx`）；引不出来，说明这条设计没有上游。
- **引擎无关的机制设计落点未定**（`design/` 顶层 vs `design/gameplay/`）：已登记为 [Q-002](../requirements/open-questions.md)，定了再落文档。
- 需求未确认的部分不做设计承诺，需要拍板的登记为 `Q-xxx`。
- 按**更小的部分逐步分解执行**：一个主题一篇文档，不写大而全的总设计。总设计是这些文档的副产物，不是前提。

## 每个引擎目录里放什么

- `README.md`：该线的索引与当前状态（薄）
- `NN-<主题>.md`：一个主题一篇，例如分层、调度与主循环、体素数据与网格化、渲染管线、存档
