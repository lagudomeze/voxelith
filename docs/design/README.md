# 设计

**边界**：这里回答"怎么做"——结构、模块、数据流、取舍。**不写**"要什么"（那属于 [requirements/](../requirements/README.md)）。设计中发现需求缺口，回到对话里问，不要在这里替用户拍板。

## 引擎无关的模型（顶层）

| 文档 | 内容 |
| --- | --- |
| [ecs-model.md](ecs-model.md) | 这个游戏在 ECS 视角下是什么：纯数值内核、三层、消息清单、交互与 UI 的边界 |
| [atoms.md](atoms.md) | L0 原子：组件与纯函数——自底向上的第一层 |

**这一层不认引擎。** 它只描述组件、系统、消息与数值，两条引擎线都必须实现它；只有真的取决于引擎的取舍，才允许写进 `bevy/` 或 `godot/`。

## 两条引擎线

| 目录 | 路线特征 | 状态 |
| --- | --- | --- |
| [bevy/](bevy/README.md) | 全 Rust，自己掌控渲染与调度；用 Bevy 的 ECS 与插件体系 | 待评估 |
| [godot/](godot/README.md) | 引擎负责渲染/编辑器/场景；Rust 走 GDExtension，或 GDScript 为主 | 待评估 |

选型定下来后写进 `engine-decision.md`。结论落定前两条线各自成立，**不要把一条线的假设写进另一条**。

## 共同约束

- 每条设计都要引用它服务的需求条目（`REQ-xxx`）；引不出来，说明这条设计没有上游。
- 引擎无关的内容写顶层，别下沉到某条线里。
- 按**更小的部分逐步分解执行**：一个主题一篇文档，不写大而全的总设计。

## 每个引擎目录里放什么

- `README.md`：该线的索引与当前状态（薄）
- `NN-<主题>.md`：一个主题一篇，例如调度与主循环、体素网格化、渲染管线、存档
