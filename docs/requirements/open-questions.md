# 待澄清问题

读原始讨论时，**答不上来的**都登记在这里，一条一个 ID。禁止在文档里写"视情况而定"——那是没登记的问题。

## 图例

| 图例 | 含义 |
| --- | --- |
| 🟥 阻塞编码 | 不定下来就无法动手写代码 |
| 🟨 影响设计 | 可以先写代码，但设计会分叉 |
| 🟩 只需确认 | 结论已经明确，只差你点头回写 |

## 条目格式

```markdown
### Q-001 🟨 <一句话问题>
- 状态：开放
- 问题：<具体问什么；给出候选并列出各自代价，比开放式提问好回答>
- 候选：A / B / C —— 各自的代价
- 倾向：<推荐哪个 + 理由；没有倾向就写"无">
- 为什么重要：<它挡住哪条需求或哪个设计决定>
- 影响面：需求 / 设计
```

## 硬规则：已答即移出

**一旦拍板，条目就从下方清单里删掉**，只在底部「已确认」表留一行结论与日期。

> 旧项目在这条上翻过车，原话留在 `legacy` 的 `docs/OPEN-QUESTIONS.md` 里：
> 「该问题早在 Q18 那一行就被一并解决（**这就是本文件腐烂的典型：底部说解决了，顶部还挂着 🟥**）」
>
> 状态字段挡不住这种腐烂——**只有移出清单挡得住**。被推翻、被取代而不再需要的条目也不许悄悄删掉，进底部「已删除留痕」表。

## 问题清单

### Q-001 🟨 引擎选型：Bevy 还是 Godot？

- 状态：开放
- 问题：最终用 Bevy（全 Rust）还是 Godot（Rust/GDExtension 或 GDScript）实现？两条线是并行评估后二选一，还是各自都可能成立？
- 候选：
  - **A** 只做 Bevy：全 Rust，渲染与调度自己掌控，重构前的 `legacy` 走的也是这条
  - **B** 只做 Godot：引擎负责渲染/编辑器/场景，Rust 走 GDExtension 或 GDScript 为主
  - **C** 两条线并行评估后再选：信息最全，但每份设计要做两遍
- 倾向：无（等原始讨论）
- 为什么重要：决定 [design/](../design/README.md) 下哪条线是主线，也决定后续分解出的子部分形态
- 影响面：设计（并间接影响需求里对性能、迭代速度、平台目标的取舍）

### Q-002 🟨 引擎无关的机制设计放哪？

- 状态：开放
- 问题：`legacy` 的战斗三篇里，主体是**引擎无关**的游戏机制（对抗判定、效果原语、相位与时间控制、怪物决策槽），只有少数是 Bevy 专属。现在 `design/` 按引擎分成了 `bevy/` 与 `godot/`，这类内容没有落点。
- 候选：
  - **A** 放 `docs/design/` 顶层：两条线共用的上层设计，`bevy/` 与 `godot/` 只放实现
  - **B** 放 `docs/design/gameplay/`：明确独立成块，但多一层目录
  - **C** 各自复制进两条线：每条线自洽，代价是同一套机制要写两遍、还会各自漂移
- 倾向：**A** —— 它本来就是两条线共用的上层设计，为它单开目录属于"为分类建目录"
- 为什么重要：不先定，机制设计会以 Bevy 的语汇写进 `bevy/`，godot 线要么重写、要么被 Bevy 假设污染
- 影响面：设计

### Q-005 🟨 要不要"伤害类型"（火 / 冰 / 物理）这一层？

- 状态：开放
- 来源：`legacy` 三篇战斗文档互相不一致（`combat.md` 写 `Ice`、`combat-mechanics.md` 写 `Frost`/`Arcane`），而最新的 `combat-design.md` 全文不再出现 `DamageType`——抵抗被表达成 `TargetStat(armor)`。于是"元素伤害"这类需求在旧设计里**没有落点**。
- 问题：新体系里，伤害类型是需求的一部分吗？如果是，它由什么承载（词汇 ID / 专门的抗性表 / 不做类型只做数值）。
- 候选：**A** 不要类型，抗性就是护甲类数值；**B** 类型用词汇 ID 表达，抗性按类型查表；**C** 类型固定枚举（放弃"加类型不改代码"）
- 倾向：无——这是玩法问题，不是技术问题
- 为什么重要：它决定属性/抗性/状态这几块设计有没有"类型"这个维度；晚定会波及内容格式
- 影响面：需求（并直接约束设计）

### Q-006 🟨 移动与技能动作是什么关系？

- 状态：开放
- 来源：`legacy` 的 `combat-design.md` 原则 4 写"一次只执行一个动作"，但移动设计（`movement.md`）要求移动独立于技能；旧 `OPEN-QUESTIONS` 的 Q28 列了 A/B/C 三案并倾向 C（**前摇锁、后摇放**），**始终没有拍板**。
- 问题：走一格算不算"那个动作"？
- 候选：
  - **A** 移动占行动槽（走一格 = 一个动作）：原则自动成立，代价是挪一步少打一下
  - **B** 移动是 Idle 时的默认行为：能边跑边打，但打断/反制管不到移动
  - **C** 移动独立成通道，但受动作阶段门控（前摇锁、后摇放）：由时间轴本身回答，且让"前摇"成为可被外人观测、可被插进来的独立窗口
- 倾向：**C** —— 威胁/反制机制本身就要求前摇是独立且可观测的时间段
- 为什么重要：决定"一次只执行一个技能动作"这条需求的措辞，也决定时间轴是否要拆成前摇/释放点/后摇三段
- 影响面：需求 + 设计

### Q-007 🟨 打断与反制的有效窗口到哪为止？

- 状态：开放
- 来源：`legacy` 旧 `OPEN-QUESTIONS` 的 Q29，未拍板。当时的实现里"后摇"没有实体（行动实体在释放点就被销毁），所以打断只能命中前摇；但设计上倾向把后摇并进同一个行动实体（"后摇即冷却"）。
- 问题：打断只对前摇有效，还是也能命中后摇？
- 候选：**A** 只对前摇有效，写成规则；**B** 后摇也可被打断（等于可以取消别人的冷却）
- 倾向：**A** —— 否则后摇并入行动实体后，打断会变成"取消冷却"这种没人想要的副作用
- 为什么重要：它同时决定 `Dispel` / `Interrupt` 这类效果的有效窗口，以及冷却是否独立于动作实体
- 影响面：需求 + 设计
