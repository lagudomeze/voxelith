# 待澄清问题

读原始讨论时，**答不上来的**都登记在这里，一条一个 ID。禁止在文档里写"视情况而定"——那是没登记的问题。

## 图例

| 图例 | 含义 |
| --- | --- |
| 🟥 阻塞编码 | 不定下来就无法动手写代码 |
| 🟨 影响设计 | 可以先写代码，但设计会分叉 |
| 🟩 只需确认 | 结论已经明确，只差你点头回写 |

## 条目格式

```markdown
### Q-001 🟨 <一句话问题>
- 状态：开放
- 问题：<具体问什么；给出候选并列出各自代价，比开放式提问好回答>
- 候选：A / B / C —— 各自的代价
- 倾向：<推荐哪个 + 理由；没有倾向就写"无">
- 为什么重要：<它挡住哪条需求或哪个设计决定>
- 影响面：需求 / 设计
```

## 硬规则：已答即移出

**一旦拍板，条目就从下方清单里删掉**，只在底部「已确认」表留一行结论与日期。

> 旧项目在这条上翻过车，原话留在 `legacy` 的 `docs/OPEN-QUESTIONS.md` 里：
> 「该问题早在 Q18 那一行就被一并解决（**这就是本文件腐烂的典型：底部说解决了，顶部还挂着 🟥**）」
>
> 状态字段挡不住这种腐烂——**只有移出清单挡得住**。被推翻、被取代而不再需要的条目也不许悄悄删掉，进底部「已删除留痕」表。

## 问题清单

### Q-001 🟨 引擎选型：Bevy 还是 Godot？

- 状态：开放
- 问题：最终用 Bevy（全 Rust）还是 Godot（Rust/GDExtension 或 GDScript）实现？两条线是并行评估后二选一，还是各自都可能成立？
- 候选：
  - **A** 只做 Bevy：全 Rust，渲染与调度自己掌控，重构前的 `legacy` 走的也是这条
  - **B** 只做 Godot：引擎负责渲染/编辑器/场景，Rust 走 GDExtension 或 GDScript 为主
  - **C** 两条线并行评估后再选：信息最全，但每份设计要做两遍
- 倾向：无（等原始讨论）
- 为什么重要：决定 [design/](../design/README.md) 下哪条线是主线，也决定后续分解出的子部分形态
- 影响面：设计（并间接影响需求里对性能、迭代速度、平台目标的取舍）

### Q-002 🟨 引擎无关的机制设计放哪？

- 状态：开放
- 问题：`legacy` 的战斗三篇里，主体是**引擎无关**的游戏机制（对抗判定、效果原语、相位与时间控制、怪物决策槽），只有少数是 Bevy 专属。现在 `design/` 按引擎分成了 `bevy/` 与 `godot/`，这类内容没有落点。
- 候选：
  - **A** 放 `docs/design/` 顶层：两条线共用的上层设计，`bevy/` 与 `godot/` 只放实现
  - **B** 放 `docs/design/gameplay/`：明确独立成块，但多一层目录
  - **C** 各自复制进两条线：每条线自洽，代价是同一套机制要写两遍、还会各自漂移
- 倾向：**A** —— 它本来就是两条线共用的上层设计，为它单开目录属于"为分类建目录"
- 为什么重要：不先定，机制设计会以 Bevy 的语汇写进 `bevy/`，godot 线要么重写、要么被 Bevy 假设污染
- 影响面：设计
