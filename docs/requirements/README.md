# 需求：澄清与确认

**边界**：这里只写"要什么"——目标、玩家能感知的行为、边界与不做的事。**不写**技术方案、目录结构、引擎选择，那些属于 [design/](../design/README.md)。

**仓库只存已确认的需求。** 还没定的不写进来——在对话里定，定完再落这里。

## 目录内容

| 文件 | 内容 | 状态 |
| --- | --- | --- |
| [00-original-discussion.md](00-original-discussion.md) | 原始讨论，逐字归档，需求的唯一来源 | 待收录 |
| [requirements.md](requirements.md) | 已确认的需求条目（`REQ-xxx`） | 待提炼 |

## 工作流

1. **归档**：原始讨论逐字进 [00-original-discussion.md](00-original-discussion.md)，不删改、不总结。
2. **提炼**：从原文摘出候选需求，逐条与用户确认；歧义、矛盾、缺口都在这一步问清。
3. **落地**：确认过的才写进 [requirements.md](requirements.md)。写不出一条需求的判定标准，说明它还没定，留在对话里。

**没进 `requirements.md` 的东西，设计阶段当它不存在。**

## 写需求条目的规矩

- 一条一个 ID（`REQ-xxx`），一句话说清"谁、在什么情况下、能做什么"。`R<n>` 属于 `legacy` 的旧规则编号，新需求不许占用。
- 每条必须能指回[原始讨论](00-original-discussion.md)的原文位置，或指回某次用户确认（带日期）。
- 必须有可验证的判定标准。
- 明确不做的事也要记（`REQ-xxx 不做：…`），免得设计阶段反复回头。
