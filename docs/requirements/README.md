# 需求：澄清与确认

**边界**：这里只写"要什么"——目标、体验、规则与边界。**不写**技术方案、数据结构、判定做法、引擎选择，那些属于[设计](../design/README.md)。

**仓库只存已定下来的。** 还没定的不写进来——在对话里定，定完再落这里。

**旧设计只是参考**（[D-007](../decisions.md)）：条目里的出处只表示这个想法最初出自哪里，不代表旧设计有约束力；不合适就改，改完在行内注明日期。

## 两层

| 层 | 文件 | 写法 |
| --- | --- | --- |
| **粗略需求** | [requirements.md](requirements.md) | 一页纸：一句话、五条设计支柱、体验目标、十几条"要什么" |
| **细则** | 按领域拆开的七个文件 | 每条一句"要什么" + 判定标准 + 出处 |

判断一条该放哪层：**说不清"这是什么游戏"放上层；说不清"具体要什么效果"放下层。**

## 编号

`C-xx` 是粗略需求；细则按领域前缀 `GP` / `WD` / `SY` / `CT` / `PR` / `QL` / `SC`。**编号只增不改**；被推翻或降级的移到 [scope.md](scope.md) 并注明日期。

## 工作流

1. **归档**：原始讨论逐字进 [00-original-discussion.md](00-original-discussion.md)，不删改、不总结。
2. **提炼**：从原文摘出候选需求，逐条与用户确认；歧义、矛盾、缺口都在这一步问清。
3. **落地**：确认过的才写进这里。写不出一条需求的判定标准，说明它还没定，留在对话里。

**没进这里的，设计阶段当它不存在。**

## 写条目的规矩

- 一条一句话，说清"谁在什么情况下能做什么"或"必须保证什么"。
- 每条都要有判定标准与出处（原始讨论位置、某次确认的日期、或 `legacy` 文档路径）。
- **不写实现**：组件、字段、判定入口、消息与顺序、加载与存档的做法，一律留给设计。
- 明确不做的事也记，免得设计阶段反复回头。
